# PWNC Content Editing Manual

Scope: changing the content of an existing page through the Frontend. Creating pages, navigation and publication status: [Site structure](<pwnc:SKILLS/Site structure/SKILLS.md>). Declaring editable elements and template syntax: [Template manual](<pwnc:SKILLS/Template manual/SKILLS.md>). Asset ids: [Media](<pwnc:SKILLS/Media/SKILLS.md>). Arranging a page from layout components (Layout mode): [Layout](<pwnc:SKILLS/Layout/SKILLS.md>). Text format and the `0x1F` multilingual format: see README.

## Mental Model

**A page is a flat document plus a template.** The document maps keys to `(type, value)`. The page template and the component templates selected in it compute the *structure*: which keys exist, their types and nesting. The structure depends on the data itself (selected component templates, repeat counts).

**The structure is the schema, enforced on every save.** A write loads the buffer, computes the structure from the data as loaded, applies the change and saves only keys whose id and type exist in that structure. Everything else is deleted silently. Consequences:
- a write with a wrong `type`, or to an address that is not in the structure, stores nothing, yet still counts as a change (undo step, "modified" marker);
- values orphaned by an earlier change (another component template, a lowered repeat count) survive exactly until the next write, then are gone.

**The rendering is output, not storage.** It shows the stored value or the template default, formatted, link-resolved and in the current language. Never write back what you read from the rendering.

**A template is a program.** It can show data from other pages, the database or plugins, show one value several times, or bind an address that renders nothing. Not everything visible is editable here.

**Edits go to a buffer.** The live version changes only when the buffer is applied.

**One field holds every language.** Writing replaces all languages at once.

**Workflow** for one text:
1. GET the page with `content_option=8439`; check `tp-marker` for a pending foreign draft; note `data-tp-index` and `data-tp-type` of the element.
2. GET its edit form (Reading a Value); the raw value is the hidden field `value`.
3. POST `range`, `type`, `value` (complete, all languages) to the page URL.
4. Verify in the response or the edit form. Applying is a separate step that needs the user's word.

## One Endpoint, Many URLs

`pwnc/module/content.php` serves every page, to visitors and editors alike. The mode comes from `content_option` and your rights, not from the address.

Readable addresses are generated stubs, one per navigation node and language:

```php
<?php /* generated by PWNC - do not edit */ namespace cms; $_GET["content_directory_index"] = "<node>"; $_GET["content_display"] = "directory"; $_GET["content_index"] = NULL; $_GET["cms_select_language"] = "<lang>"; require("../pwnc/module/content.php");
```

- The stub selects a navigation node and a language. The node resolves to a content index, following `directory://` aliases; a node pointing elsewhere answers with a redirect.
- Stubs of the same node in different languages (their file names may differ per language) render the same document with the same addresses. The language lives in the URL, not in the document.
- The identity of a page is its content index. Address elements by index and range, not by the URL you came through.
- Stubs are rewritten whenever the navigation changes. Never edit one. A foreign file at a stub's path is kept, and the stub gets a `-1` suffixed name instead.

Direct call, also for pages without a navigation entry:

```
/pwnc/module/content.php?content_index=<index>&content_option=<mode>
```

Without `cms_select_language` the language is your last selected one (remembered per user), else `Accept-Language`, else the default. `content_user=<user>` works on pages in that user's content workspace and needs rights on it.

## Editing Modes

`content_option` is a bitmask; each bit enables the editing layer for one element class. Anything not enabled renders as output.

`1` href · `2` plugin · `4` text · `8` value · `16` download · `32` image · `64` thumbnail · `128` media · `256` template · `512` group · `1024` repeat · `2048` shift (legacy) · `4096` alternative blocks · `8192` conditional blocks · `16384` debug · `32768` switch

| Preset | Value | Bits |
|--------|------:|------|
| Output | `0` | none |
| Content | `8439` | href, plugin, text, download, image, thumbnail, media, conditional blocks |
| Layout | `44808` | value, template, group, repeat, shift, switch, conditional blocks |
| Full | `45055` | Content + Layout |

- Without update rights on the page you get the published output whatever `content_option` says.
- With update rights every mode, `0` included, renders the **buffer** plus the toolbar. Mode `0` shows the draft as visitors will see it after apply, not what they see now.
- A bit only takes effect if its edit action exists for you: download, image/thumbnail, media and template elements additionally need access to the Download, Image, Media and Template apps. Without it those elements render as plain output in every mode.
- An element with `edit="off"` in the template never gets an editing container.
- The mode survives navigation: generated links and redirects carry `content_option`.

### Conditional and Alternative Blocks

`cblock` renders when the element named by its `idref` has a non-empty value, or, with `regex`, when that value matches. `calt` renders when its `idref` element is empty. Both test the effective value (stored or default) in the current language, so a section can show in one language and not in another. Writing a value can switch whole sections on or off.

| Enabled bits | `cblock` | `calt` |
|--------------|----------|--------|
| neither | by condition | by condition |
| `8192` | always | never |
| `4096` | by condition | always |
| both | always | always |

All presets except Output force conditional blocks, so elements behind an empty condition stay reachable, and every else branch ("no image set") disappears while editing. Full excludes `4096` on purpose: with both bits the if and the else branch render together. Use both only to reach an element inside a `calt`.

### Editing-Only and Output-Only Blocks

`edit` blocks render only while editing (an `edit` block may list element classes and then needs one of them enabled), `noedit` blocks only in output. Settings tables above a component are `edit` blocks; the markup that applies those settings is often `noedit`. Editing modes swap whole regions, so never judge layout or wording from an editing render.

### Debug Mode

Bit `16384`, in no preset; add it to a mode or send it alone (behaves like output). It wraps elements in HTML comments:

```html
<!-- #debug# text id:tp_content.tp1.t1 -->…<!-- #debug# /text id:tp_content.tp1.t1 -->
<!-- #debug# cblock idref:tp_content.tp1.fax -->…<!-- #debug# /cblock idref:tp_content.tp1.fax -->
```

- The llm view drops comments: request debug renders with `view: raw`.
- `id:` is the data address. `idref:` is the only place that names the element a conditional block depends on.
- `edit`/`noedit` regions, the final pass of a repeat (`(final)`) and template errors (`error: redundant closing tag`) are marked too.
- With `interface.template.operator` the toolbar gains the document tree command (see Reading a Value).

## Finding What to Edit

**Content index**: the toolbar marker `<label id="tp-marker">(<index>) <title></label>`, and `object=<index>` in every toolbar command URL.

**Element containers** (`tp-dd`, `tp-dd100` for templates and groups) carry:

| Attribute | Meaning |
|-----------|---------|
| `data-tp-index` | data address: `range` for value writes, edit forms and `#reference` |
| `data-tp-path` | structural address: `range` and `value` for structural commands |
| `data-tp-type` | the type to post back, already mapped (`switch` → `value`, `thumbnail` → `image`) |
| `data-tp-value` | effective raw value, only on image, thumbnail, media, download, template, repeat, switch, shift |
| `data-tp-reference` | sync source id, on the root of a synced element |
| `data-tp-title`, `data-tp-name` | element title; name of the selected component template |
| `data-tp-cmd` | toolbar commands offered here |
| `data-tp-dd-type` | internal type number for drag & drop, not a `content_option` bit (image: `64`, bit `32`) |
| `data-tp-empty` | the container renders nothing |

- Index and path differ only when the template binds data with a prefix modifier (`.name`, `..name`). Take each from its own attribute.
- Copy addresses from the markup, never compute them. Auto-numbered ids do not follow visible positions (a repeat's first item can be `r1.2`).
- The page head defines `tp_code` (edit action per element type, keyed by `data-tp-dd-type`; third entry: accepted drop types) and `tp_command` (URL template per structural command). They are the exact specification of each request: `%index%`, `%path%`, `%value%`, `%return%` (user input) are the placeholders.
- Empty text elements render their title as `<span class="tp-placeholder">` while editing. Value and switch elements render nothing in output; while editing they show title and a value cut to 25 characters.
- `left`, `top` and `id` (`data-tp-id`) in command URLs are scroll and highlight helpers; omit them.

## Reading a Value

The stored raw value comes from the Backend edit forms, read from the buffer:

```
/pwnc/module/interface.php?ifc_message=<form>&ifc_option=external&ifc_page=content&object=<index>&range=<data-tp-index>
```

| Type | `<form>` |
|------|----------|
| `text` | `edit_range` |
| `value` (switch included) | `edit_value` |
| `href` | `edit_href` |
| `plugin` | `edit_plugin` |

The raw value is the hidden field `value`, verbatim with raw `0x1F`. Image, thumbnail, media, download, template, repeat and switch values are read from `data-tp-value`; the toolbar picks asset and template ids through their apps, but a known id can be posted directly.

**Defaults.** A template element may declare `default`. The page and `data-tp-value` show stored-or-default; the edit forms return the stored value only.

| `clear` in `data-tp-cmd` | Form returns | Meaning |
|--------------------------|--------------|---------|
| no | empty | empty |
| yes | value | stored value |
| yes | empty | showing the template default |

Writing over a default stores an override; `#clear` removes it and the default shows again. An element with a default cannot be made empty: an empty stored value falls back to the default.

**Whole document.** `ifc_message=debug` (same parameters, no `range`; needs `interface.template.operator`) lists the structure as a tree: id, path, type, stored value (truncated), default. Defaults appear for repeats and templates only. An element declared twice in the template (e.g. in `edit` and `noedit`) is listed twice; both entries are the same key.

**Draft preview.** `ifc_message=analyze` (no `range`) renders the buffer without the editing layer: plain text, word statistics, full HTML in `ifc_param1`. Self-links in it resolve against the Backend (`interface.php`).

## Writing a Value

Post to the page URL (stub or `content.php?content_index=…`), not to the edit form's own `action`, which only re-renders the form:

| Field | Value |
|-------|-------|
| `range` | `data-tp-index` |
| `type` | `data-tp-type` |
| `value` | the complete new raw value |

Keep `content_option` in the URL. The response is the page re-rendered in that mode; there is no error message, so verify the value in the response or the edit form. GET with the same parameters works as well; the browser sends structural commands as GET.

| Type | Value |
|------|-------|
| `text` | PWNC text format, multilingual |
| `value` | plain text, multilingual |
| `href` | multilingual URL: `content://<index>`, `directory://<node>`, `mailto:…`, absolute URL; query and anchor allowed |
| `plugin` | URL, `content://`/`directory://` included |
| `image` | `image://<id>` (thumbnails too) |
| `media` | `media://<id>` |
| `download` | `download://<id>` |
| `template` | component template id |
| `repeat` | number of repetitions; `0` = automatic |
| `value` for a switch | `1` on, empty off |

- The write replaces the whole value of every language. Read first, change, send everything. The MCP `post` tool also accepts a multilingual object (`{"": default, "<lang>": …}`).
- Plugin: the server fetches the URL while rendering and embeds the response; a status ≥ 300 or a failure embeds nothing. The edit form has no language selector and shows `https://` as placeholder for an empty value.
- Writes are read-modify-write of the whole buffer without locking. Two writers on the same page at once can overwrite each other's change.

## Structural Commands

Same fields; `type` is the command, `range` is `data-tp-path`, `value` as listed:

| `type` | `value` | Effect |
|--------|---------|--------|
| `#buffer` | ignored | copy the element and its subtree to your clipboard; empty response |
| `#paste` | ignored | **replace** the element with the clipboard content |
| `#copy` | target path | overwrite the target with the source |
| `#swap` | target path | exchange source and target |
| `#clear` | ignored | delete the stored value and, for templates and groups, all values below |
| `#drop1` / `#drop2` | ignored | remove the element; the run behind / before it closes the gap |
| `#kick1` / `#kick2` | `±n` | open a slot, see below |
| `#reference` | sync source id | bind to a sync source (`range` = `data-tp-index`) |

- `data-tp-cmd` is a menu, not a gate, and uses toolbar names: `copy` = `#buffer`, `release` opens sync source creation (`ifc_message=pool_add`), `source`/`export` open the Template app. `#copy` and `#swap` are what drag & drop (`#dragdrop2`, `#dragdrop1`) send.
- The clipboard belongs to your user, persists, and works across pages.
- The server checks no compatibility. Moved values are fitted by id and type into the target; a value without a same-type slot in the target is deleted. An incompatible `#swap` (e.g. text with image) deletes both values. Check compatibility first: the target's accept mask in `tp_code` must contain the source's `data-tp-dd-type` (most types accept only themselves; image/thumbnail and value/switch accept each other).

### Shifting and Dropping

`#kick*` and `#drop*` operate on a **run**: every element at the same nesting depth as the given one, inside its nearest enclosing `template` or `group` (the whole page if there is none), from the element towards the end (positive) or the start (negative). Each element of the run moves to the next same-type position in that direction. Consequences:

- The run crosses containers: at the same depth, items of a neighbouring repeat inside the same group belong to it.
- Elements of other types in the run move too, each among its own type, and lose data by the same rule.
- An element with no position left is deleted.

Kick (direction = sign of `value`, magnitude = positions; the command name does not matter, the toolbar sends `+n` for `#kick1`, `-n` for `#kick2`). Three texts A, B, C, kick on B:

| | Result | Lost |
|---|--------|------|
| `#kick1`, `+1` | A, –, B | C |
| `#kick2`, `-1` | B, –, C | A |

The free slot is always at the element's position. `#kick1` on an item of an automatic repeat first adds `n` slots, so nothing falls off; this does not apply to elements nested inside an item's own group or template. `#kick2` never adds slots: the first element of its run is lost unless its slot is empty.

`#drop1`/`#drop2` remove the element and pull the run behind it / before it one position closer. Use kick and drop only where the run is uniform (the items of one repeat); in mixed runs they shift and delete elements of other types.

### Repeats and Component Templates

- Automatic repeat (never written or `0`): renders up to the last filled slot; never written, at least the template default, `0` without that minimum. Editing renders with the repeat bit enabled add one empty slot to fill. Items vanish on their own when dropped; no count change is needed.
- Pinned repeat (`> 0`): exactly that many items. Lowering it below the filled items hides the surplus; the next write deletes it. Raise it before kicking into a full pinned repeat.
- Switching a `template` element to another component template orphans the old component's values; the next write deletes those that do not fit the new one. Switching back does not restore them; undo does.
- Shift (legacy, bit `2048`): writing `type=shift`, value `±n`, moves all direct children `n` same-type positions with the kick loss rule. Prefer kick and drop.

## Synced Elements

A sync source is a registered `(page, path, type)`; other pages bind elements to it.

- **Storage**: the binding page keeps one pointer `<key>:#reference:<source id>`. On load the source's extract is expanded below the key; on save only the pointer and local overrides are written.
- **Recognising**: the root carries `data-tp-reference="<source id>"`; it and all expanded elements have class `tp-ref`.
- **Binding**: post `type=#reference`, `value=<source id>`, `range=<data-tp-index>`. Sources are listed at `interface.php?ifc_message=pool&ifc_option=external&ifc_page=content`. Creating a source needs `interface.content.pool.operator`.
- **Freshness**: a source is a file extracted from the **published** version of its page, refreshed when that page is applied. Editing the source page changes nothing elsewhere until apply. A source created from an unpublished element is empty until then.
- **Visitor cache**: published output is cached per page; the cache is not invalidated by source updates. A binding page can serve its old rendering until that entry is rebuilt (the binding page's own apply, a navigation or template change, clearing the content cache; [Diagnostics](<pwnc:SKILLS/Diagnostics/SKILLS.md>), section Caches). Editing renders are never cached.
- **Editing a binding**: writing an element below the root stores a local override for that key only; the rest keeps syncing. Writing the root itself replaces the pointer and ends the binding. To change the content everywhere, edit the source page and apply there.

## Buffer and Publication

Every page has one buffer shared by all editors: text plus metadata (title, description, keywords, image, page template; edited via the toolbar's metadata form, `ifc_message=meta`). Commands go to the page URL with an **empty** `range`:

| `content_message` | Effect |
|-------------------|--------|
| `apply` | copy the buffer to the live version, store it as a version, refresh sync sources of this page |
| `revert` | reset the whole buffer to the live version |
| `undo` / `redo` | step through the buffer text history |

A non-empty `range` turns the request into a write and the command is ignored. Every command answers `303` to the page, changed or not.

- **Pending state**: `<label id="tp-marker" class="tp-mod">` (localized "modified" date appended) and the toolbar commands to apply and discard. Clean: no `tp-mod`. "Undo (n)"/"Redo (n)" show the available steps. Any write sets the pending state, including writes that stored nothing.
- **History**: up to nine undo steps per page, shared by all editors, covering the buffer text only. Metadata changes are not undone. `revert` is itself a step: undo after revert restores the text.
- **Rights**: apply needs the same update rights as writing. On a published page apply is live at once. On a draft it only updates the stored version; visitors get `410` until the page is published ([Site structure](<pwnc:SKILLS/Site structure/SKILLS.md>)).
- **Backups**: the Editor app (`ifc_page=content`) stores versions (`version_store` saves the current buffer; applied states are stored automatically) and retrieves them into the buffer. Use it before editing into a foreign draft.
- A buffer can hold weeks-old changes of other editors. `revert` and `apply` act on all of them.

Publication is the user's decision. Do not apply because your own change is finished. Check for pending changes first and report a foreign draft instead of applying or discarding it.

## Permissions

- Viewing a page needs `content.reader.<index>`; without it the request redirects to login.
- Writing, apply, revert, undo and redo need update rights: either the page belongs to your content workspace (or `content_user`'s) and your content role allows updating at the page's status, or you hold `content.writer.<index>` and the page is published.
- Writing a page in status *document* resets it to *draft*; writing a published page keeps it published.
- Asset and template elements need access to the corresponding app (see Editing Modes); the document tree needs `interface.template.operator`.

Details on access strings: [Permissions](<pwnc:SKILLS/Permissions/SKILLS.md>).

## Troubleshooting

| Symptom | Cause |
|---------|-------|
| Element not in the markup | mode bit not set, manager access missing, `edit="off"`, or hidden by a `calt`/`noedit` region |
| Marker shows modified, value unchanged | wrong `type`, or address not in the structure |
| Markup or `&amp;` appears as literal text | value rebuilt from the rendering instead of the edit form |
| A link inside a text lost its target | same cause; `content://`/`directory://` replaced by a rendered URL |
| One language empty | the write carried only one language |
| Elements vanished after kick/drop/swap | run reached its end, mixed-type run, or incompatible swap target |
| Content vanished one write later | lowered repeat count or switched component template |
| Visitors see the old version | buffer not applied, page not published, or (synced elements) cached rendering |
| Change on the source page did not reach bound pages | source page not applied, or binding detached by writing its root |
| `content_message` ignored | `range` not empty |
