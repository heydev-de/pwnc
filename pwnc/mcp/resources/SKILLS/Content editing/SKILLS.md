## Introduction

The frontend is both the public website and its editing surface: the same URL serves a visitor and an editor, the latter with an editing layer around every element the template exposes. There is no separate content API — you request a page with an editing mode and post back to the same URL. Your permissions on that page decide what you see and may change.

Declaring the editable elements is the template author's job; see the [Template Manual](../Template%20manual/SKILLS.md).

---

## Mental Model

**A page is a tree of addressable elements.** The template decides which parts are editable and gives each one a path. Editing means writing a value to a path.

**The rendered page is output, not storage.** What you see is the stored value after formatting, link resolution and language selection. Never write back what you read from the rendering.

**A template is a program.** Templates are fully scripted and can read anything — other content nodes, database records, plugin output, request state. So a page may show much that belongs to no editable path, one value may appear several times or in transformed shape, and an addressable element may render nothing.

**Changes go to a buffer first.** Editing never touches the live page; a separate publication step applies the buffer, and visitors see the old version until then.

**One field holds all languages.** `/de/x.php` and `/en/x.php` are usually the same document with the same paths, so writing a value replaces every language at once.

## One Endpoint, Many URLs

`pwnc/module/content.php` is the only frontend endpoint. It renders the public page and the editing layer alike — which mode you get depends on `content_option` and on your rights, not on the address.

The readable addresses are generated stubs. A page file contains nothing but a few parameters and the include:

```php
<?php /* generated by PWNC - do not edit */ namespace cms;
$_GET["content_directory_index"] = "aB3kL9xQ";
$_GET["content_display"]         = "directory";
$_GET["content_index"]           = NULL;
$_GET["cms_select_language"]     = "en";
require("../pwnc/module/content.php");
```

The stub names a navigation node and a language; the content index is resolved from the node. Two consequences matter when editing:

**The language lives in the URL, not in the document.** `de/home.php` and `en/home.php` are two stubs pointing at the *same* node `aB3kL9xQ`, differing only in `cms_select_language`. They therefore render the same content document with the same element paths — which is why one field carries every language, and why writing one language alone deletes the others.

**The path is not the identity.** A page is identified by its content index, and the same content can be reached through any stub that resolves to it. Address elements by index and range, not by the URL you happened to use.

The stubs are generated from the navigation and rewritten when it changes. Never edit one, and never expect a hand-made file at such a path to survive.

### Calling the Endpoint Directly

A stub is not required. Backend modules — the editorial system among them — address the endpoint straight away:

```
/pwnc/module/content.php?content_index={index}&content_option={mode}
```

That is the route to a page with no navigation entry, and the one to prefer when you already know the index and do not care which readable path leads there. One further parameter appears on those URLs: `content_user` renders the page in that user's workspace instead of your own.

Without a stub no language is preselected, so the page renders in the current one. When the language matters, either use the stub for that language or set `cms_select_language`.

## Quick Start: Change One Text

```
1. get   /en/page.php?content_option=8439
         → find the element, note data-tp-index and data-tp-type

2. get   /pwnc/module/interface.php?ifc_message=edit_range&ifc_option=external
         &ifc_page=content&object={index}&range={path}
         → the raw value is in <input name="value">

3. post  /en/page.php?content_option=8439
         range={path}   type=text   value={the edited raw value}

4. get   /en/page.php?content_option=8439
         → verify; publishing is a separate step and needs the user's word
```

Step 2 is not optional. It is the only place the stored value is visible.

## Editing Modes

`content_option` decides how much of the editing layer is rendered. It is a bitmask; each bit enables one class of element. Anything not enabled renders as plain output, so an element you cannot see is not missing — the mode did not ask for it.

### The content_option Bitmask

| Bit | Element class |
|-----:|---------------|
| `1` | Links |
| `2` | Plugins |
| `4` | Texts |
| `8` | Values |
| `16` | Downloads |
| `32` | Images |
| `64` | Thumbnails |
| `128` | Media |
| `256` | Templates |
| `512` | Groups |
| `1024` | Repeat |
| `2048` | Shift *(legacy)* |
| `4096` | Alternative blocks |
| `8192` | Conditional blocks |
| `16384` | Debug |
| `32768` | Switches |

`shift` is a legacy element type: `#kick1`/`#kick2` do the same job, so it survives only in older templates. Treat one you meet as read-only and move the run with the kick commands instead.

### Presets

The toolbar offers four combinations:

| Mode | Value | Shows |
|------|------:|-------|
| Output | `0` | the page as a visitor sees it |
| Content | `8439` | texts, links, images, thumbnails, media, downloads, plugins, conditional blocks |
| Layout | `44808` | templates, groups, repeats, shifts, switches, values, conditional blocks |
| Full | `45055` | everything except alternative blocks and debug |

Use **Content** for wording and assets, **Layout** to move, duplicate or insert structure, **Output** to check the result. A request without `content_option` renders output.

### Conditional and Alternative Blocks

A template can make part of a page depend on whether an element holds a value. `cblock` renders its content when the referenced element has one, `calt` renders when it is empty; together they form an if/else. A `cblock` may also carry a `regex`, in which case it renders when the referenced value matches that pattern rather than merely being non-empty — so writing a value can switch a whole section on or off.

For editing this matters more than it appears, because **the editing modes override the condition**:

| Enabled | Conditional block | Alternative block |
|---------|-------------------|-------------------|
| neither | as the condition says | as the condition says |
| Conditional blocks (`8192`) | always rendered | suppressed |
| Alternative blocks (`4096`) | as the condition says | always rendered |
| both | always rendered | always rendered — the if branch and the else branch at once |

Four things follow, and they explain the presets:

**Content and Layout both enable conditional blocks.** In those modes you see every conditional section, including ones no visitor can currently see. That is the point: an element hidden behind its own empty condition could otherwise never be filled, because it would not be in the markup to address.

**The else branch disappears while editing.** A placeholder like "No image set" is gone the moment you switch to Content or Layout, because a conditional block being force-shown suppresses its alternative.

**Full deliberately leaves alternative blocks out.** Enabling both would render the if and the else branch simultaneously — useful only when you specifically want to reach an element inside an else branch.

**An editing mode is not a preview.** What you see there is a superset of the published page. To judge what a visitor gets, request the page with `content_option=0`.

### Editing-Only and Output-Only Blocks

A template can also mark a region as belonging to one side or the other: an `edit` block exists only while editing, a `noedit` block only in the output. The settings tables that appear above a section — "Background image", "Parallax" — are `edit` blocks; the markup that actually places that image is `noedit`.

So the difference between an editing mode and the output is not just added handles: whole regions are swapped. Never judge layout or wording from an editing render.

### Debug Mode

Bit `16384`, in none of the presets. Add it to the mode you are working in, or request it alone to see the plain page annotated.

Every template element is then wrapped in HTML comments naming its type and id, and conditional blocks name the element their condition reads:

```html
<!-- #debug# text id:t_slogan -->…<!-- #debug# /text id:t_slogan -->
<!-- #debug# cblock idref:i_background -->…<!-- #debug# /cblock idref:i_background -->
<!-- #debug# edit -->…<!-- #debug# /edit -->
<!-- #debug# /repeat id:r1 (final) -->
```

That `idref` is worth the request on its own: nothing else in the markup says which element a conditional block depends on, and debug parses alternative blocks far enough to report theirs even when they are being force-shown. The `edit` and `noedit` markers show which regions belong to which side, and repeats mark their final repetition.

The toolbar also gains a "Debug info" command, which opens the [document tree](#the-document-tree).

## Finding What to Edit

### The Content Index

Every page has a numeric content index. You need it for reading values and for metadata actions, and the control panel states it in three places:

```html
<label id="tp-marker" …>(42) example page</label>
```

```html
<div id="tp-ctrl-permission">… content.reader.42 | content.writer.42 …</div>
```

Every command URL the panel builds carries it as `object=42` as well. The marker is the shortest read: the number in parentheses before the page title.

### Ranges

Each editable element carries its address in the markup:

```html
<div class="tp-dd" data-tp-id="4Nq7Zx"
     data-tp-index="r1.4.tp_content.tp1.r1.2.t3"
     data-tp-path="r1.4.tp_content.tp1.r1.2.t3"
     data-tp-type="text"
     data-tp-cmd="copy paste swap kick1 kick2 drop1 drop2 release reference clear">
```

| Attribute | Use |
|-----------|-----|
| `data-tp-index` | the address for reading and writing a **value** |
| `data-tp-path` | the address for **structural** commands |
| `data-tp-type` | pass back verbatim as `type` |
| `data-tp-value` | the current value, on the types that expose one, see [Reading a Value](#reading-a-value) |
| `data-tp-title` | the element's description from the template |
| `data-tp-cmd` | the structural commands this element accepts |
| `data-tp-dd-type` | the element's type for moves, see [Moving and Duplicating](#moving-and-duplicating) |
| `data-tp-empty` | present when a container holds nothing |

`data-tp-cmd` depends on the element's state: `clear` appears once the element's *effective* value is non-empty — which includes a value the template supplies as a default and that was never written.

`data-tp-dd-type` uses the internal element-type numbers, not the `content_option` bits — an image carries `data-tp-dd-type="64"` while the `content_option` bit for images is `32`. Do not mix the two.

Index and path are usually identical, inside repeats as well. They diverge only when the template addresses the element with a prefix modifier — `.name` binds the data to the enclosing template's base, `..name` to an absolute key — which lets a template point several positions at one stored value. When they differ, using the wrong one edits the wrong thing, so take each from its own attribute rather than assuming.

`data-tp-type` is already the name the server expects on the way back. Two element types are declared under one name and posted under another — `switch` is posted as `value`, `thumbnail` as `image` — but the attribute has that mapping applied, so copying it is always correct.

### The Document Tree

`data-tp-*` only describes what the current mode rendered. For the whole document at once, ask the content module:

```
/pwnc/module/interface.php?ifc_message=debug&ifc_option=external
&ifc_page=content&object={index}
```

It answers with a nested list of every element in the buffer — `id`, `path`, `type`, the stored `value` and the `default`. That is the fastest way to learn a page's shape, and the only view that shows stored value and default side by side.

Three limits: it needs the `interface.template.operator` permission, values are cut to the first 50 words, and the `default` column is filled for repeats and templates only — a `default` on a text, value, image or link renders on the page but shows up empty here.

A path may also appear twice, once in each branch of a conditional. Both entries address the same element.

### Reading the Page as a Visitor Sees It

```
/pwnc/module/interface.php?ifc_message=analyze&ifc_option=external
&ifc_page=content&object={index}
```

The content analysis renders the **buffer** without the editing layer and offers it three ways: the page as plain text, word statistics, and the complete HTML source in `<input name="ifc_param1">`. It is the way to check an unpublished draft without publishing it. Self-referencing links resolve against the interface module rather than the page, so judge content, not URLs.

## Reading a Value

Assets are chosen from their manager and have no editing form. Everything else has one, and which message you use depends on the type:

| Element type | Read with |
|--------------|-----------|
| `text` | `ifc_message=edit_range` |
| `value`, `switch` | `ifc_message=edit_value` |
| `plugin` | `ifc_message=edit_plugin` |
| `href` | `ifc_message=edit_href` |

```
/pwnc/module/interface.php?ifc_message=edit_range&ifc_option=external
&ifc_page=content&object={index}&range={path}
```

Not every type exposes its value in the page. The rendering carries `data-tp-value` only for types whose editing action needs the current value:

| Carries `data-tp-value` | Does not |
|-------------------------|----------|
| `image`, `thumbnail`, `media`, `download`, `template`, `repeat`, `switch`, legacy `shift` | `text`, `value`, `href`, `plugin` |

For the first group the page is enough — `image://7Kd2mQpR` on an image, `3` on a repeat. For the second, use the form.

**An empty read does not mean the element is empty.** A template element may declare a `default`, and the two paths treat it differently: the page renders the stored value *or* the template's default, while the editing form returns the stored value alone. So an element can render text and still read back empty — it is sitting on its default and has never been written.

`data-tp-cmd` tells the two apart, because `clear` is offered exactly when the *effective* value is non-empty:

| `clear` present | Form returns | Meaning |
|-----------------|--------------|---------|
| no | empty | genuinely empty, the page shows a placeholder |
| yes | a value | the value was written and is stored |
| yes | empty | the element is showing its template default |

In the third case a write does not edit the visible text, it overrides the default — and there is no command that restores the default afterwards, since `#clear` only removes what is stored.

**Read this way, always.** The rendered page shows the value after formatting: `[+ bold]` has become `<b>`, `[directory://x label]` has become an absolute `<a href>` that even carries your own `content_option`, and paragraph breaks have become `<br>`. Rebuilding a value from that output writes markup as literal text and destroys every link in the element.

## Writing a Value

Post to the page URL — the same URL you rendered, not to the interface module:

| Field | Meaning |
|-------|---------|
| `range` | the element address |
| `type` | the element type, as given in `data-tp-type` |
| `value` | the complete new value |
| `content_option` | keep the mode you are working in |

The write replaces the element's whole value. There is no partial update, which is why you read first.

### Where Values Come From

| Type | Value is |
|------|----------|
| `text` | PWNC text format, multilingual |
| `value` | plain text, multilingual |
| `href` | a URL, multilingual — `content://12`, `directory://abc`, `mailto:…` or an absolute URL |
| `plugin` | an absolute URL, single-valued — the form offers no language selector |
| `image`, `thumbnail` | `image://{id}` from the image manager |
| `media` | `media://{id}` from the media manager |
| `download` | `download://{id}` from the download manager |
| `template` | a template id from the template module |
| `repeat` | the number of repetitions, `0` enables auto mode |

A plugin is the one type whose value the server acts on while rendering: it fetches that URL and embeds the result, so a slow or unreachable target slows the page down for every visitor. Its form starts on `https://` when the element is empty — that is a placeholder, not a stored value, and the interface drops it again on save.

Asset ids are listed by the corresponding module — `interface.php?ifc_page=image` shows every image with its `image://…` id. The browser reaches those managers through a popup that hands the selection back, but that round trip is a convenience: knowing the id, post it directly.

### Text Format and Languages

Text fields use PWNC's own format — not HTML, not Markdown. Paragraph breaks are real newlines, `&` is a literal `&`, and formatting uses bracket notation:

```text
[+ bold]  [/ italic]  [< big]
[content://12 label]  [directory://abc label]  [IMG image://7 250]
```

Multilingual values put every language into one string, separated by the raw byte `0x1F`:

```text
default text[0x1F]en:English text[0x1F]de:Deutscher Text
```

Both formats are specified in the platform instructions returned by `readme_first`. Read them there rather than deriving them from a rendering. Sending only one language deletes the others.

## Structural Commands

Structural changes use the same three fields, with a command in `type` and the element's `data-tp-path` in `range`:

| `type` | Effect |
|--------|--------|
| `#buffer` | copy the element to the clipboard |
| `#paste` | insert the clipboard here |
| `#swap` | exchange with the element named in `value` |
| `#copy` | duplicate to the element named in `value` |
| `#kick1` | insert above, pushing the rest down |
| `#kick2` | insert below, pushing the rest up |
| `#drop1` | remove, pulling the rest up |
| `#drop2` | remove, pulling the rest down |
| `#clear` | empty the element |
| `#reference` | bind the element to a sync source, see [Synced Elements](#synced-elements) |

`data-tp-cmd` lists what the interface offers on that element. It is a menu, not a gate — the endpoint accepts any of these commands on any element, including `#copy`, which no element ever lists. What constrains a command is the element's type and its place in the document, so read `data-tp-cmd` as advice about what makes sense here, not as a permission check.

### Moving and Duplicating

Two commands involve a second element. `range` names the source, `value` the target's `data-tp-path`:

```
range={source path}   type=#swap   value={target path}
```

`#swap` exchanges the two, `#copy` writes the source over the target.

A browser drag sends `#dragdrop1`, a drag with Alt sends `#dragdrop2`, and the server treats them as `#swap` and `#copy` respectively. There is no separate drag interface to reproduce — use the two commands directly.

Not every pair may be combined. Each element declares its type in `data-tp-dd-type`, and the page's `tp_code` map carries an accept mask per type as the third entry of each row. The move is allowed when the **target's** mask contains the **source's** type:

| Element | Accepts |
|---------|---------|
| most types | their own type only |
| image, thumbnail | either of the two, so they are interchangeable |
| value, switch | either of the two, so they are interchangeable |

Checking beforehand is worthwhile: the interface simply refuses a move it does not allow.

### Shifting a Run of Siblings

`#kick1` and `#kick2` insert nothing. They shift a run of elements along, and they are the only commands here that can destroy content.

The operation is bounded by the element's nearest `template` or `group` ancestor. Within that bound it takes every sibling on the same level and of the same type, starting at the given element and proceeding in the shift direction, removes each from its position and re-inserts it a number of compatible positions further along.

**An element for which no compatible position remains in that direction is removed and not put back.** That is the data loss to guard against: count the compatible positions ahead before shifting.

The direction is carried by the sign of `value`, not by the command name — both route to the same operation, and the browser merely negates the number for one of them. The magnitude is how many compatible positions each element moves.

| Command | Sends | Moves the run | Frees a position |
|---------|-------|---------------|------------------|
| `#kick1` | positive `value` | towards the end | at the element, so the space opens *above* it |
| `#kick2` | negative `value` | towards the start | after the element, so the space opens *below* it |
| `#drop1` | `value=1` | — | removes the element, following siblings move up |
| `#drop2` | `value=-1` | — | removes the element, preceding siblings move down |

The interface labels the two kicks "insert above" and "insert below" for that reason: what you gain is the free position, and the run is what pays for it.

Repeats are where this bites most often, because the instances of a repeat are exactly such a run of same-type siblings. The rule is about the run, though, not about repeats: a repeat counts itself and keeps one empty slot free, so there is normally a position to take. Only a repeat pinned by a given value (`type=repeat`) can run out, and then you raise that value first. Writing `0` releases the pin and the repeat counts itself again.

## Synced Elements

An element can be offered as a shared source and reused on other pages, so one edit reaches every place it appears.

**How it is stored.** A page that uses a source keeps only a pointer — the type `#reference` and the source's id. On load PWNC expands the source into the document; on save it writes the pointer back, never the expanded values. One source can carry a whole sub-tree, so the expansion may cover several elements.

**Recognising one.** A synced element carries `data-tp-reference` with the source id, and its container has the class `tp-ref`.

**Binding one.** `#reference` is an ordinary write whose `value` is the source's id. Offering an element *as* a source is not a content write at all: the `release` command opens the editorial module with `ifc_message=pool_add`, which registers page, range and type as a new entry.

**When changes travel.** A source is not read live. Its text is cached in a file that is refreshed when the page holding the source is **published** — applying a page re-syncs every source on it. Editing a source changes nothing elsewhere until that page is applied.

**Editing a synced element detaches it.** Writing a value to a key that came from a source stores a local value and clears its reference mark, so later resolutions leave that key alone. The pointer stays, and the source's other elements keep syncing. To change the content everywhere, edit it on the source's own page and publish there — editing the copy silently turns it into a copy.

## Buffer and Publication

Every change lands in a buffer belonging to the page. The published version stays untouched until the buffer is applied.

| `content_message` | Effect |
|-------------------|--------|
| `apply` | publish the buffer |
| `revert` | discard the buffer completely |
| `undo` | step back one change |
| `redo` | step forward one change |

Send these to the page with an **empty** `range`. With a range set, the request is treated as a write and the command is ignored. A successful command answers with a 303 redirect back to the page.

Whether the buffer holds pending changes is visible in the markup, not only in the toolbar. With a clean buffer the page marker reads

```html
<label id="tp-marker" …>(42) example page</label>
```

and after a write it gains a class and a timestamp:

```html
<label id="tp-marker" class="tp-mod" …>(42) example page (Modified now)</label>
```

At the same time "Apply changes", "Discard changes" and "Undo (n)" appear in the toolbar, where `n` is the number of steps available. That is the reliable signal that your write arrived. "Redo (n)" only joins them once you have actually stepped back — its absence means there is nothing to step forward to, not that the command is unavailable.

Three things matter before editing into an existing draft:

- `revert` discards the **whole** buffer, including work that was not yours
- the step history is a ring of ten states, so you can undo at most nine changes and older ones are gone
- a buffer can predate your session by weeks

Publication is the user's decision. Do not apply a buffer because your own change looks finished — check whether pending changes exist, and if a foreign draft is in the way, say so and ask.

## Permissions

Access is granted per page:

- `content.reader.{index}` — may see the page and its editing layer
- `content.writer.{index}` — may change it

An accessor without writer rights receives output regardless of `content_option`. Do not infer capabilities from the markup; the exposed toolbar is authoritative.

## Traps

**The rendering is not the value.** The most expensive mistake available here: it silently turns markup into literal text and internal links into absolute URLs.

**All languages live in one field.** Write the complete multilingual string or you delete the languages you left out.

**`#kick1`/`#kick2` can delete.** An element with no compatible position left in the shift direction is removed and not put back.

**`revert` is not undo.** It discards everything pending on that page, from every author.

**`range` decides what kind of request this is.** Set, PWNC writes to that element and ignores `content_message`. Empty, PWNC runs the `content_message` command. Sending both does not do both — the range wins, and the command is silently dropped.

## Troubleshooting

| Symptom | Cause |
|---------|-------|
| Element not in the markup | `content_option` does not enable its class, or you lack reader rights |
| Markup appears as literal text on the page | the value was rebuilt from a rendering instead of read through the edit form |
| A link inside a text lost its target | same cause; the stored `content://` or `directory://` form was replaced by the rendered URL |
| One language suddenly empty | the write carried only the other language |
| An element vanished after a shift | `#kick1`/`#kick2` with no compatible position left in that direction |
| No "Apply changes" in the toolbar | the buffer holds no pending changes, so the write did not arrive |
| `content_message` had no effect | `range` was not empty |
| Change invisible to visitors | the buffer was never applied |
| An edit to a shared element did not reach the other pages | the element detached on write, or the source's page was not published |
